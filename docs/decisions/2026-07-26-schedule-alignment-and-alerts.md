# 排程時段全面對齊，並補上警示的兩層

- 日期：2026-07-26
- 狀態：已採用
- 影響範圍：`ai-news-digest`、`java-learn-digest`、`digest-cron`（Cloudflare Worker）、`pmset`

> 這份記錄從「今天沒收到信」查起，一路挖到三層原因。第一層（等網路的順序）是最先發現的，
> 但它只是讓失敗訊息變誠實；第二層（喚醒時間沒對齊）才是真正讓信寄不出去的原因；
> 第三層（警示又慢又有漏）是查證過程中才發現的。三層都修了，依序記在下面。

## 症狀

2026-07-26 沒收到每日新聞信，只收到雲端 14:00 最後一班發的「⚠️ 今天沒有可寄的 AI 新聞」警示信。

第一直覺是「筆電整天沒開機」，但 `run.log` 顯示本機當天被 launchd 觸發了 5 次：08:11、10:30（每週）、12:15、13:03、13:31（每日，13:03 那班是每日 + 每週補跑撞在一起）。機器有醒，只是每一班都死在同一個地方：

```
2026-07-26 12:15:04 WARN: git pull 第 1/3 次失敗：Could not resolve host: github.com。5 秒後重試。
2026-07-26 12:30:53 WARN: git pull 第 2/3 次失敗：Could not resolve host: github.com。5 秒後重試。
2026-07-26 12:46:18 WARN: git pull 第 3/3 次失敗：Could not resolve host: github.com。5 秒後重試。
2026-07-26 12:46:18 WARN: state 分支同步失敗，放棄本時段（避免用過期狀態誤判）。
```

## 這是 DarkWake，不是沒開機

`Could not resolve host` 是 DNS 完全解不到，代表網路介面根本還沒起來。這正是 macOS 的 **DarkWake**：筆電在「電池 + 闔蓋」時被排程鬧醒，CPU 跑得動、螢幕不亮，但 WiFi 受電源管理限制不一定連得上。

另一個佐證是時間戳對不上：13:31:31 那行寫著「5 秒後重試」，下一次重試的時間戳卻是 13:48:36，中間隔了 17 分鐘。這不是程式慢，是程序在 DarkWake 期間被系統凍結、機器再次淺醒才解凍繼續跑。純軟體 bug 不會有這種時間斷層，看到它就該往電源管理想。

這也不是單日意外。`state/` 裡的警示紀錄 `noprep-2026-07-06`、`07-12`、`07-16`、`07-21`、`07-26` 大約每一到兩週出現一次，全是同一個病。

## 根因：等網路的邏輯擺在 git 同步後面

`run_ai_news.sh` 本來就寫了 `wait_for_network()`，會每 5 秒探測一次、最多等 120 秒，就是為了對付「喚醒後 WiFi 慢幾十秒才連上」。

問題是它的呼叫點在產稿迴圈裡（原本第 205 行），而主流程一開場（原本第 176 行）就先 `git_pull` 同步 state 分支。執行順序變成：

```
開場 → git pull（DNS 掛，5 秒間隔重試 3 次）→ 放棄本時段 → 直接 exit 1
                                                    ↑
                                    wait_for_network 在這之後，永遠跑不到
```

於是專門為 DarkWake 寫的等待機制形同虛設。更嚴重的是它把整套可靠性設計一起廢掉了：多時段補跑的前提是「每一班都真的有嘗試」，但只要那天筆電都在闔蓋狀態，每一班都在同一秒被 DNS 打死，五班等於零班。

`git_pull` 失敗就放棄整個時段這件事本身是對的（拿過期狀態會誤判「已寄過」而漏寄，這是先前的教訓），不該改。要改的是別讓它在網路還沒好的時候就被呼叫。

## 決策

在主流程最開頭、任何連外動作之前呼叫 `wait_for_network()`，失敗才放棄本時段：

```sh
echo "===== ... 開始 ... =====" >> "$LOG"

if ! wait_for_network; then
  log "WARN: 網路未就緒，放棄本時段（留待下個補跑時段）。"
  exit 1
fi

# ── 同步 state 分支 ──
```

產稿迴圈裡原有的那次呼叫保留，防的是跑到一半斷線；網路正常時它會立即返回，沒有成本。

效果：DarkWake 醒來後最多等 2 分鐘讓 WiFi 連上，通了才碰 git。真的整段沒網路（例如人在外面沒連線）就照舊放棄，交給下一班——這時放棄是合理的，跟現在「還沒等就放棄」是兩回事。

## 為什麼不選其他做法

**改用 `pmset disablesleep` 或 `caffeinate` 讓機器整天醒著**——這是跟系統省電機制對著幹，耗電發熱，而且為了一封信讓筆電全天不睡代價太大。本專案的一貫取捨是順著系統設計走（多時段補跑 + marker 去重），不是強迫機器配合。

**只把 `git_pull` 的重試間隔從 5 秒拉長到 60 秒**——治標。它讓 pull 撐久一點，但沒有「網路好了就馬上繼續」的能力，會固定浪費時間，而且下一個連外動作（抓 RSS、呼叫 claude）還是各自要面對同樣的問題。既然已經有寫好的探測函式，讓它跑在正確位置比較乾淨。

**在 launchd plist 加更多時段**——增加撞到 FullWake 的機率，但沒解決「醒著卻用不了網路」這個真正的問題，只是把賭注加大。

## 怎麼驗證有效

短期看 log：DarkWake 班次應該出現「網路在 120s 內未就緒，本時段放棄」而不是「Could not resolve host」。前者代表等待機制有跑、只是這次真的沒網路；後者代表順序又被改回去了。

長期看 `state/`：`noprep-YYYY-MM-DD` 的出現頻率應該明顯下降。如果還是一到兩週一次，表示 120 秒不夠 WiFi 連上，那就調大 `NET_WAIT_MAX`（目前 24，即 24×5=120 秒），而不是回頭改順序。

# 第二層：喚醒時間沒跟著備稿時段搬

## 順序修好了，信還是寄不出來

修完順序後去看隔壁的 `java-learn-digest`，發現它**兩週前（7/14，commit `0d51c61`）就修過同一個問題**，
註解寫的理由跟上面推導的一字不差。它修完之後 `noprep-*` 就停在 07-14，而 ai-news 一路噴到 07-26 —— 
修正本身有效，只是沒同步過來。

但關鍵是：**java-learn 今天一樣沒備成稿。**

```
2026-07-26 10:29:54 WARN: 網路在 120s 內未就緒，本時段放棄。
2026-07-26 13:15:48 WARN: 網路在 120s 內未就緒，本時段放棄。
2026-07-26 14:13:35 WARN: 網路在 120s 內未就緒，本時段放棄。
```

修過順序的專案，今天三班全滅。差別只在失敗訊息變誠實了——從「Could not resolve host」
變成「等了 120 秒網路還是沒好」。**第一層修正讓 log 說實話，但救不回這種狀況。**

## 真正的原因

```
$ pmset -g sched
Repeating power events:
  wakepoweron at 7:05AM every day
```

定時 FullWake 只有早上 07:05 一次，但兩個專案的備稿時段是 ai-news 12:15/12:50/13:30、
java-learn 10:00/13:00/20:00 —— **沒有一班貼在 07:05 後面**。07:05 那次真喚醒沒人用，
中午那些班全靠 launchd 自己把機器戳醒，而那是 DarkWake，網路不會起來。等 120 秒也不會好，
因為問題不是「WiFi 慢幾十秒」，是「這個狀態下根本不供網路」。

`pmset repeat` **全機只能設一組重複喚醒**，這是硬限制：不可能每個專案、每個時段各配一個。

## 決策：所有時段對齊整點，讓需要保證的班共用同一個喚醒點

| 時間 | 誰 | 做什麼 |
|---|---|---|
| 08:00 | 雲端 | java-learn 寄出前一天備好的課；週六順帶寄週報 |
| **12:00** | **pmset + 本機** | **唯一保證的備稿班**——喚醒與排程同一個整點，靠開頭那 120 秒等待吸收喚醒延遲 |
| 13:00 | 本機 | 備稿補救班（靠「你人在電腦前」的機會） |
| 14:00 | 雲端 | ai-news 寄出；兩邊當天最後一班，做缺稿體檢 |

「喚醒與排程排在同一分鐘」看似會搶跑，但正因為第一層已經把等網路挪到最前面，
launchd 先醒、腳本等 WiFi 上線再動作，兩者剛好接上。**第一層修正在這個方案裡從「有比較好」變成「非有不可」。**

備稿時段刻意不排晚班：最後一班太晚的話，失敗了也沒時間補救。

### 順帶處理的三件事

**備稿排在寄出的前一天。** 週報改週六備、週日寄；月報改當月倒數第二天備、最後一天寄
（每日信維持當天備當天寄）。原本週報月報是當天備當天寄，一失敗就零緩衝。
順帶修掉月報的月份錯位：以最後一天為寄出日之後，`date +%Y-%m` 算出的 marker 自然對上內容涵蓋的月份。

**週報月報從本機直寄改成走 outbox 由雲端寄。** 三種週期同一條路，本機不再直接寄任何信。
這同時消滅了「本機直寄沒有雲端兜底、失敗完全靜默」的整條路徑。

**一個 launchd job 依序跑三種週期**（`run_slot.sh`），不是三個 job 各排同一個整點——
同時觸發會搶同一個 worktree 的 git `index.lock`，先到的成功、後到的莫名其妙失敗。

### 「當月最後一天」不能寫死日期

launchd 的 `Day` 只能填固定數字，31 在小月不觸發、2 月更短。改成每天觸發、由 `outbox.py`
用「明天是不是 1 號」判斷，任何月份長度都成立。這段邏輯有測試釘住（`tests/test_outbox.py`
涵蓋大月、小月、平年 2 月、閏年 2 月、跨年月）。

## 為什麼不選其他做法

**用 `pmset disablesleep` 或 `caffeinate` 讓機器整天醒著**——跟系統省電機制對著幹，耗電發熱，
為了幾封信讓筆電全天不睡代價太大。本專案的一貫取捨是順著系統設計走。

**只把 `git_pull` 的重試間隔從 5 秒拉長到 60 秒**——治標。它讓 pull 撐久一點，
但沒有「網路好了就馬上繼續」的能力，而且下一個連外動作還是要各自面對同樣問題。

**在 launchd 加更多時段**——增加撞到 FullWake 的機率，但沒解決「醒著卻用不了網路」，只是把賭注加大。

# 第三層：警示又慢又有漏

## 盤點出來的實況

查證過程順手盤了一次「出事的時候你什麼時候會知道」，結果六種失敗裡只有兩種會通知到，
其中一種還遲到 25 小時：

| 情境 | 原本的警示時間 |
|---|---|
| ai-news 每日沒稿 | 當天 14:00 |
| java-learn 每日沒稿 | **隔天 14:00**（備的是明天的課，等雲端發現時已經過了一整天） |
| java-learn 每週沒稿 | ❌ 不發（`daily-send.yml` 沒稿只 `echo` 一行就結束） |
| ai-news 每週 / 每月沒稿 | ❌ 不發（本機直寄，整條路徑沒有雲端參與） |

延遲的根源是「警示信一律由雲端發」。當初這樣設計是因為本機失敗最常見的原因就是沒網路，
沒網路就寄不出信。但這把兩種情況混為一談了：「沒網路」和「有網路但產稿失敗」該走不同的路。

## 決策：兩層警示，各自負責一種失敗

**第一層——本機最後一班失敗，當下就寄。** 涵蓋「有網路但失敗」，延遲 0。
寄成功才寫 `alert-<kind>-YYYY-MM-DD` marker 並推上 state 分支。

**第二層——雲端 14:00 體檢兜底。** 涵蓋「本機完全沒連上」，那種情況本機寄不出任何東西。
看到 marker 就不重複寄。ai-news 這層改成掃過當天所有該寄的週期，缺項列在同一封信；
java-learn 這層加了「明天的課備好了嗎」，把那個 25 小時的延遲壓成當天。

marker 的寫入順序不可顛倒：**一定要確認寄信成功才寫**。反過來會變成「沒信也沒人知道」。
可以接受的邊角情況是信寄成功但 marker 推不上去，那會收到兩封重複的——這個方向的錯誤是安全的。

## 沒有紀錄，本身就是紀錄

原本最難除錯的不是「失敗了」，是**「沒跑」跟「沒去看」長得一模一樣**：機器沒醒 → launchd 沒觸發 →
`run.log` 連「開始」那行都沒有。7/26 這次就是靠逐行比對時間戳才確定機器其實是醒著的。

所以每個時段都固定留一行 `RESULT <kind> OK|SKIP|FAIL <說明>`。平常只寫在本機 `run.log`；
只有「最後一班仍然失敗」那天，才把當天的 RESULT 彙整成 `state/attempts-YYYY-MM-DD.log`
推上 state 分支，讓警示信直接引用。平常成功的日子 state 分支保持乾淨。

**而「連 attempts 檔都沒有」是有意義的訊號**：代表本機一次都沒能連上 GitHub。
警示信必須把這句話明確寫出來，不能寫成「查無資料」——那會讓人誤以為是系統壞了，
而不是筆電整天沒醒。

## Cloudflare 那層為什麼不另外做 log

Worker 每次 dispatch 都有 `console.log`（`observability` 開著），但要登入後台才看得到，實務上不會去看。
不需要另外做：**Worker 有沒有開槍，看 GitHub 有沒有出現對應時間的 run 就知道**
（`gh run list --workflow daily-send.yml`），而且收到警示信這件事本身就證明 Worker 活著。

唯一無解的靜默失敗是 Worker 自己死掉——那樣不會收到信、也不會收到警示信。
要補得加一層外部 health check（例如 Worker 每天 ping healthchecks.io，逾時就通知），
這次刻意不做：它跟時段對齊沒有相依，是獨立的一件事。

# 第四層：固定班次本身就會漏（7/27 追記）

## 對齊完的隔天就又沒信

7/27 兩個備稿班都失敗，14:00 收到雲端警示信。第一時間的猜測仍然是「筆電沒開」，
但 log 說的是另一回事：

```
11:50–12:02   airportd 持續 auto-join 掃描，一直沒關聯上任何網路
12:00:04      備稿開跑
12:02:02      等滿 120 秒放棄  ← RESULT daily FAIL 網路未就緒
12:04:09.916  en0 關聯上手機熱點（WPA3_SAE）
12:04:09.932  DHCP en0: publish success { IPv4, DNS, DHCP }   ← 網路真正可用
12:29:19      Clamshell Sleep（闔蓋）
13:00:01      第二班開跑，此時已在 DarkWake，12:58–13:05 的 publish success 為 0
```

機器從 11:50 到 12:29 都是 FullWake、螢幕亮著。**不是沒開機，是網路晚了 2 分 7 秒。**

## 兩個獨立的問題

**一、120 秒對熱點太短。** 連手機熱點不是單純關聯 WiFi：Mac 要先透過藍牙把 iPhone 叫醒、
iPhone 才開始廣播、然後關聯、再走 DHCP。log 顯示 Mac 從 11:50 起就一直在掃描重試，
十幾分鐘才成功。`NET_WAIT_MAX=24`（120 秒）是照「固定 WiFi 喚醒後慢個幾十秒」設的，
對熱點差得遠。

**二、固定班次的窗口對不上。** 把當天「醒著且有網路」的時間畫出來：

```
12:00  ├─ 第一班（12:02 放棄）              ✗ 早了 4 分鐘
12:04  ┌────────────────────────┐
       │  醒著 + 有網路的 25 分鐘  │          ← 沒有任何一班在這裡
12:29  └────────────────────────┘  闔蓋
13:00  ├─ 第二班（DarkWake，沒網路）        ✗ 晚了 31 分鐘
```

兩班一早一晚，剛好把唯一能用的窗口夾在中間。**問題不是班次太少，是班次綁在固定時刻、
而不是綁在「有網路」這個條件上**——再多排幾班也只是多買彩券。

## 決策：加寬等待窗，並改成事件驅動

**A. `NET_WAIT_MAX` 24 → 90**（120 秒 → 450 秒）。用當天的數字驗算：
`12:00:04 + 450s = 12:07:34`，比網路通的 `12:04:09` 晚三分半，會等到。
代價趨近於零——真的沒網路時只是多空轉，那時機器本來就在睡。

**B. launchd 加 `WatchPaths`**，網路設定一變就觸發，不再只靠時刻表。
配 `ThrottleInterval=180` 限制最快 3 分鐘一次；launchd 本身不會讓同一個 Label
同時跑兩份，所以不需要另外上鎖。

監看路徑要選對：**`/etc/resolv.conf` 是 symlink**（指向 `../var/run/resolv.conf`），
WatchPaths 監看 symlink 不可靠，要直接寫 `/var/run/resolv.conf`。
另外加 `/Library/Preferences/SystemConfiguration` 當第二道，但它幾天才變一次，
不能當主力。

**時間窗擋住無意義的觸發**（寫在 `run_slot.sh`，兩種觸發來源共用）：

| 專案 | 窗 | 理由 |
|---|---|---|
| ai-news | 12:00–13:45 | 太早新聞還沒上架湊不足 10 則；太晚雲端 14:00 已寄過或警示過，稿綁當天週期、隔天作廢 |
| java-learn | 08:00–23:00 | 備的是明天要寄的課，跟今天幾點備無關，晚上補到也有效 |

**窗外觸發刻意不寫 `run.log`**，只覆寫一個 `.last-trigger.log` 時間戳。網路設定一天會變很多次，
每次記一行的話幾百行雜訊會把真正要看的 `RESULT` 淹掉——而 `RESULT` 能拿來除錯的前提
就是它夠稀疏。想確認 WatchPaths 有沒有在動時看那個檔就好，檔案不會長大。

## 為什麼不是多排幾個固定班

7/27 就算排了 12:00 / 13:00 / 14:00 三班也一樣全落空——能用的窗口只有 12:04–12:29。
固定班次的覆蓋率取決於運氣，而事件驅動的覆蓋率取決於「網路有沒有通」，
後者才是真正的前提條件。多排班次還會讓 `run.log` 更難讀。

## 怎麼驗證這些修正有效

**看 log 的失敗訊息換了沒。** DarkWake 班次應該出現「網路在 120s 內未就緒」而不是
「Could not resolve host」。前者代表等待機制有跑，後者代表順序又被改回去了。

**看 `RESULT` 行的數量。** 每天該有的備稿班都要留下一行。少一行就是那個時段沒被觸發，
往電源管理查，不要往程式查。

**看 `state/` 裡 `alert-*` 的出現頻率。** 對齊喚醒之後應該明顯下降。如果還是頻繁出現，
先確認 `pmset -g sched` 的喚醒時間有沒有跟備稿時段脫節，再考慮調大 `NET_WAIT_MAX`（目前 90，即 450 秒）。

**確認 `WatchPaths` 還活著。** `cat .last-trigger.log` 看最後一次窗外觸發的時間戳；
如果那個檔的日期停在很久以前，代表事件驅動那條路已經失效，只剩固定班在撐。
也可以用 `launchctl print gui/$UID/com.kilin.ai-news` 看 `event triggers` 區塊還在不在。

## 給未來的自己

看到 `run.log` 出現「Could not resolve host」或「網路未就緒」時，**別急著推論成「筆電沒開機」**——
7/26 和 7/27 兩次都不是。先照這個順序查：

1. **機器那時醒著嗎**：`pmset -g log | grep '^<日期> 1[12]:'`，看有沒有 Sleep / DarkWake 事件。
   沒有就代表是 FullWake，問題出在網路不是電源。
2. **網路是什麼時候通的**：`log show --start "<日期> 11:58" --end "<日期> 12:35" --predicate 'process == "configd"' | grep "publish success"`。
   這行的時間戳就是網路真正可用的時刻，拿它跟 `run.log` 的放棄時間比對，
   差幾分鐘就知道是不是等太短。
3. `pmset -g sched` 的喚醒時間，跟第一個備稿時段是不是同一個整點
4. log 裡「N 秒後重試」的實際時間差有沒有遠大於 N（有的話是被凍結，確定是 DarkWake）
5. 手動在機器醒著時跑一次同樣的指令會不會過（會過就不是設定或憑證問題）

**三種長得很像但成因不同的失敗**，別混為一談：

| 症狀 | 真正的原因 | 該調的東西 |
|---|---|---|
| `Could not resolve host` | 等網路的邏輯排在 git 後面，根本沒跑到 | 呼叫順序 |
| `網路未就緒` + 機器全程 DarkWake | 喚醒時段跟備稿時段脫節 | `pmset` 的 `WAKE_TIME` |
| `網路未就緒` + 機器 FullWake | 等太短（熱點要好幾分鐘），或窗口沒對上 | `NET_WAIT_MAX` / `WatchPaths` |

**改任何時間之前，記得時刻表散落在五個地方**，改一處不改其他處就會像這次一樣出事：

- `launchd/*.plist.template` 與已安裝的 `~/Library/LaunchAgents/*.plist`（備稿時段、`WatchPaths`）
- `install.sh` 的 `WAKE_TIME`（pmset 喚醒，全機共用一組，兩個專案共用）
- `run_slot.sh` 的 `WINDOW_START` / `WINDOW_END`（事件觸發的有效時間窗）
- `outbox.py` 的 `is_prep_due()` / `is_send_due()`（哪天該備、哪天該寄）
- `~/Workspace/digest-cron` 的 `wrangler.toml` cron 與 `src/index.js` 的 TARGETS（雲端寄出，兩邊 key 必須一字不差）

改備稿時段時，**`WAKE_TIME` 和 `WINDOW_START` 都要跟著動**：前者決定機器醒不醒得來，
後者決定事件觸發時肯不肯做事。少改任何一個，症狀都是「排程看起來有跑但什麼都沒發生」。
